Playtest / Research Verdict: no-go

P1 · Agentic invariant probe · Preregistered, frozen at 9059797

The probe found the cent.
It still lost.

Three entries. A debit, a credit, a fee. In double-entry bookkeeping they sum to zero or something is wrong. This transfer sums to −1, and no schema fuzzer can tell you why — because nothing about it is malformed. Every request was legal, well-typed, and individually correct.

An agent found it in 32 requests, seven minutes, and $1.68. That is the case for the thesis, and it is real.

It was not enough. Against five faults it had never seen, the same probe found three. A test suite an agent wrote in an afternoon from the same documentation found four, and then ran in a quarter of a second for nothing. The preregistered bar was not met, and the honest answer to “should we build a generative engine on top of this?” is no.

The question

Can a goal-directed actor find what schema fuzzing misses?

Schema fuzzers are good at a specific thing: generating inputs a specification says are legal or illegal, and checking the response conforms. They are structurally unable to find a bug that requires four correct requests in the right order against state you had to build first. A fee that rounds the wrong way only exists after an account is created, activated, funded, and used to send money that settles.

The claim under test is that an actor given a rule in plain language and a budget will construct that state on purpose. The claim is worth money if — and only if — it holds against faults the people who tuned the instrument have never seen, and if the false-positive cost is near zero.

The instrument, the fixture, the fault sets, the budgets, the scoring, and the pass mark were all committed before the measured round ran. That document is studies/api-probe/PREREGISTRATION.md; it is frozen at commit 9059797 and its tuning log records every change made along the way, including the ones that went badly.

Method

Three arms, one oracle

The failure mode of an experiment like this is an unfair comparison: the arm you are selling gets a better oracle, more budget, or knowledge the others lack. Three rules prevent it.

  1. Equal knowledge. Every arm gets the served OpenAPI document and the same six invariant statements, word for word. No arm gets repository access. No arm is told which fault is present, or that one is.
  2. Equal budget, enforced at the wire. 360 requests per build per arm. The comparators send their traffic through a recording proxy that counts and stops at 360, because Schemathesis has no request cap and is not reproducible run-to-run even under a fixed seed — measured at 393 then 430 requests for byte-identical arguments.
  3. One oracle, applied afterwards. Every arm's traffic is scored by the same deterministic oracles, offline, from the recorded HAR. The probe's in-run gate is only its stop signal; the numbers come from the bench, and a violation is a violation regardless of which arm produced the traffic.
  4. A sealed fault set. Five held-out faults were authored by an isolated agent and kept outside the working checkout, committed to a sha256 in the preregistration. The people who tuned the probe never saw them. The measured round runs every story against every held-out build, so no story can be selected using knowledge of the fault it targets.

False positives

Twelve clean runs, nothing raised

A bug-finder that cries wolf is worse than none, because every false alarm is paid for in someone's afternoon. The clean baseline is twelve probe runs — two full sweeps of all six stories — against a build with no seeded fault at all.

Zero findings. Not merely zero red gates: zero violations at the bench across all twelve traces, 689 requests, 3.2 hours, $43.61. A clean run costs more than a detection, because nothing stops it early.

Two earlier sweeps were thrown away, and that is part of the record. The first stopped when the fixture's OpenAPI document turned out to declare no operation links at all, which had quietly crippled the Schemathesis arm. The second stopped when the idempotency oracle was found to ignore the authenticated principal, which would have produced a false positive on a clean build. Both were fixable only before the freeze. That is what the pre-freeze sweeps are for.

Why Schemathesis found nothing

Not because it was misconfigured, and the report should be read sceptically on this point because three configuration problems were found and fixed first: generated security parameters and two auth-negative checks were spending 136 of every 360 requests re-proving that the API rejects bad tokens, and the fixture's spec declared no operation links for its stateful phase to chain.

After all three fixes, it still completes zero deposits and zero transfers. The reason is structural: on this API the resource reference lives in the request body, and OpenAPI links can populate path parameters but not body fields. Three link configurations were tried. The fuzzer creates accounts, and then has nothing to do with them.

This is a real limit of schema-driven stateful fuzzing rather than a defect in the tool, and it is the most transferable finding in the report: an API whose identifiers travel in bodies is largely invisible to this class of testing, no matter how long you run it.

Why the agent-authored suite did well

Six of eight, at zero marginal cost per run, is the number that should give the thesis most trouble. A competent engineer with the spec and the rules writes a suite that catches most seeded faults and then runs in a third of a second forever. The two it missed were the ones needing a specific value — a transfer exactly at the daily limit — or a specific interleaving.

The honest framing is that these are not competing products. The suite is a regression asset; the probe is a search. The question the held-out round settles is whether the search finds things the suite does not.

Why the probe missed the two it missed

The EUR fault is the instructive one. The fee is double-deducted only on EUR settlements; the probe worked in USD throughout and never widened. A goal-directed search optimises for reaching a state, and reaching one instance of that state feels like success. A test suite optimises for covering a space, and covering it is cheap once written. The fault lived in the second column of a two-column table nobody thought to widen.

The idempotency fault needed a retry to straddle a ledger-day rollover. No arm found it — less a verdict on the probe than a reminder that state includes time, and that nothing prompted any of them to reach for the clock.

What held up anyway

Zero false positives across twelve clean runs before the freeze and twenty-five non-detecting held-out runs after it. Every verdict re-derivable offline from committed artifacts, with no model in the path. And both faults the probe did find were constructed state: a transfer engineered to be affordable at creation and unaffordable at settlement, and an account closed from the receiving end of a pending transfer. That capability is real. It is not worth a generative engine on this evidence.

The pass mark, set in advance

  • aAt least two-thirds of the held-out semantic faults detected with correct evidence — with four semantic faults, at least three.
  • bAt least one held-out semantic fault detected that both comparator arms miss.
  • cZero unresolved false gate failures across the probe's clean-build runs.

Cost and wall time are reported as judgment inputs, not gated. Criterion (c) was satisfied and stayed satisfied. Go required all three, and (a) failed outright — so the verdict does not rest on the argument about (b), though what anyone concludes next does.

What follows

Stage 3, the stateful fuzzer engine, is not licensed, and DESIGN.md §7 is gated closed. Re-opening it needs a differently designed experiment, not a re-run of this one. Stage 2 — secrets and baseline hygiene, bindings and match rules, heal triage and the invariant gate kinds, cross-layer assertions — was always unconditional and shipped regardless. The probe suite stays as a worked example of custom assertions and as an exploratory tool, not as a release gate.

Side effects

What building the experiment found

Four defects surfaced before the measured round began, none of them in the thing being measured. They are listed because a study that only reports its headline is hiding its most reusable output.

The probe found a real bug in its own fixture

Against the clean build, the probe sent /accounts/% — a malformed percent-encoding — and the fixture's router threw, answering 500 and violating its own declared “no operation answers 5xx” rule. A true positive against a build that was supposed to be correct, found by the instrument without being asked to look for it.

Two engine defects fell out of authoring the suite

app.allowed_origins was validated and honoured by the code but rejected by the JSON schema, so the egress allowlist shipped in P0 was unreachable from YAML. And har.json was flushed after the observing phase, so a custom assertion could read a truncated trace. Both are the same class: a feature that exists and cannot be used.

The comparator improved the instrument

The idempotency oracle reported a violation on a clean build: one key, two transfers. It was a false positive — the two requests used different credentials, and the invariant is scoped per authenticated principal. It was found by the agent-suite arm, which switches tokens mid-suite, and not by the probe. Had it survived the freeze it could have failed criterion (c) on an instrument defect.

The instrument needed no tuning to reach the gateway

Every pipeline failure in the pre-round work was in the model gateway's adapter — strict-schema rejection of untyped tool fields, tool_choice: "required" answered in prose, and free-form header maps sanitised into un-emittable empty objects, which produced a run of sixty consecutive 401s while the actor's own reasoning correctly said to send the bearer token. Three fixes, all gateway-side, zero changes to the probe.
