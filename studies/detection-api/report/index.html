Playtest studies · detection-api · trial 1 · 2026-07-31

Same API, same seeded bugs: a coding agent, the Playtest probe, and a fuzzer

Ten semantic faults were seeded into the Loanpoint JSON API (the web study's subject, filtered to its API-observable faults). Each arm tested the same build black-box with equal knowledge — base URL, an OpenAPI document, the same user stories — and an arm-blind judge scored every claim. The coding agent found all 10 seeded faults with zero invalid claims ($11.06, 12 minutes). The Playtest probe found 7 of 10 with a 78% noise ratio ($13.81, 90 minutes). Schemathesis found 0 seeded faults but the only genuine latent ($0, 7 seconds).

Read this first. This is the fast, indicative variant of the pre-registered design: one trial, one round, one build, reused subject and catalog, ~2.5 h wall clock end to end. Every cut from the design, and everything that went sideways, is logged in QUICK.md — including one material fairness caveat in the probe's disfavor (below).

Answer to the study's central question: API-level testing caught exactly the class of fault browser-level testing missed. Of the 4 faults both web arms missed, the API coding agent found 4/4 and the API probe 3/4. Faults whose manifestation is a wrong number or a dropped row in a JSON response are hard to see through a rendered page and easy to see in the payload.

Triggering is not detecting

Server-side telemetry (diagnostic only, invisible to all arms) shows every arm mechanically triggered all 10 fault paths. Schemathesis hit the wrong overview total 55 times and the missing late-fee charge 52 times — and reported none of them, because a fuzzer has oracles for crashes and schema shape, not for wrong values. Every seeded fault here returns well-formed, plausible, wrong JSON. Its one real find is the one fault-shaped thing in its oracle class: a reproducible-on-clean HTTP 500 when a literal JSON null body hits a body-reading route — the only latent defect any arm found.

Why the probe missed 3 — a fairness caveat that cuts against the result

Arm P's three misses (bundle-threshold, saturday-roll, available-filter) were all covered by its frozen stories, and telemetry shows its runs triggered all three paths. The deliverable contains no claim about any of them (verified by keyword sweep): the actor burned those journeys fighting request-shape discovery — most visibly the draft-creation contract — and surfaced its own confusion as findings ("draft PATCH rejects valid updates", "fresh drafts reported expired"), which the judge correctly ruled not-a-bug. That confusion is also most of the probe's 78% noise.

The confound: arm C held the full OpenAPI document in its context. The probe's actor works from story text alone — the frozen suite config set no app.openapi, though the product supports it and a customer testing an API would plausibly set it. The probe was the only arm made to rediscover the request contract by trial. The obvious follow-up: same protocol, app.openapi set. Until then, the honest reading of B2 is "a coding agent with the spec beat the probe without it", not "coding agents beat Playtest".

What was cut (abridged from QUICK.md)

  1. Subject and fault catalog reused from the web study; the 10 API-observable faults were selected mechanically (manifestation check touches only /api/*).
  2. One trial, one round, one build; no hidden clean build (B3 replaced by noise ratios; the judge still verified every latent claim against a running clean reference).
  3. No served OpenAPI doc existed, so a fresh-context agent authored one from clean source; it is the shared API-surface input (and the source of the confound above).
  4. Loanpoint has no auth, so the design's credential-role discovery was dropped with it.
  5. Arm C capped at 150 messages (cost control; it finished at 51). Arms P and C ran concurrently on independent copies.
  6. Human audit limited to low-confidence and contested rows — all were reviewed; zero overrides.
