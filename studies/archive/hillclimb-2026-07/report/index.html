01Experiment walkthrough

What was tested,
and how.

The study asked whether an AI user-testing system could repeatedly find problems, hand evidence to a coding agent, and improve the same application until the test suite stopped finding blocking issues.

The research question

Can Playtest hill-climb a deliberately broken app back toward a good user experience—and can “clean” ever mean safe to release?

“Hill-climb” means a repeated loop: test the app, repair evidence-backed problems, test again, and keep the change only when regression checks still pass. The experiment compared two ways of choosing and verifying repairs.

Fault taxonomy

What L1, L2, L3, and L4 mean

The level describes scope, not severity
L1

Surface

The page is present and works, but text, contrast, or messaging is wrong.

Example: “Free shipping” beside a $6 charge
L2

Interaction

A visible control, feedback state, validation rule, or error response fails.

Example: Add to cart succeeds silently
L3

Flow

A transition, retry, recovery path, retained value, or boundary behaves incorrectly.

Example: validation wipes payment fields
L4

Absence

A capability or local navigation route promised by the specification is missing.

Example: order history removed

    All 15 story–persona cells ran in two rounds. Actors drove the real browser; graders produced findings; a catalog-aware adjudicator labelled each finding against ground truth.

  4. 04

    A blind coding agent received the baseline findings and app specification, fixed everything it considered plausible, then ran a focused journey set plus new regression stories.

  5. 05

    A separate blind operator deduplicated issue classes, probed ambiguous findings, required a regression story for each fix, and rotated journeys toward untested risk.

    61 runs · 20 seeded faults fixed · 0 regressions

    The final catalog-aware pass separated faults the tester detected, faults repaired only through code inspection, accepted residuals, and faults still live at the end.

    156 ledgered runs · $40.99 actor/grader cost
Detection is not resolution

Did the tester name it?

Detection recall counts known faults explicitly surfaced by an actor or grader. Resolution counts faults removed by any route, including a repair agent finding adjacent bugs while reading code.

“Clean” is a local statement

Did this suite find anything new?

A clean round did not mean the app was fault-free. It meant no registered blocking finding appeared under the exercised stories and pinned regressions passed. Known faults could remain outside those paths.

Findings are not faults

One problem can produce many reports

Actors generated hundreds of observations. Adjudication removed duplicates and separated seeded faults from preferences, out-of-scope wishes, timing artifacts, and fix-induced problems.

03Investment decision

Build—but narrow
what is being built.

Under these definitions, the evidence supports more investment. It does not support replacing Playtest, freezing it at its current capability, or abandoning it.

Recommended
B
Invest more

Build

Continue funding Playtest as a behavioural test and repair-loop product.

  • Deterministic risk matrix for every critical transition
  • DOM/API contract oracles for exact business truth
  • Adversarial and semantic-audit actor modes
  • Coverage-aware reporting with “unknown” as non-green
Why: 77% resolved, zero policy regressions, 11/12 misses bridgeable
B
Replace it

Buy

Stop building Playtest and adopt an off-the-shelf alternative.

  • This experiment did not compare competing products
  • No evidence that a vendor closes the flow or oracle gaps
  • Still buy commodity browser, axe, and assertion engines underneath
Decision: not supported or ruled out without a vendor benchmark
H
Freeze investment

Hold

Keep using the current product, but stop adding capability.

  • Current version remains useful as an exploratory scout
  • But 54% recall leaves too much value unrealised
  • Measured gaps have specific, testable interventions
  • Choose only if investment capacity is unavailable
Decision: safe but strategically premature
S
Stop using

Sell

Abandon Playtest and remove it from the development process.

  • Contradicted by useful detection and repair outcomes
  • Would discard evidence unavailable from unit tests
  • Only justified if operating cost exceeds discovery value
  • The study did not measure team-level return on investment
Decision: not supported by this experiment

What “build” does not mean: do not spend first on larger models, autonomous merging, or more personas. Invest in forced coverage, independent truth checks, and build-system packaging; rerun the study to prove those changes close the measured gaps.

The boundary

Journey success is not business correctness.

06Product roadmap

What it takes to become
a release oracle.

First, define the claim

“Release oracle” can only mean safe for the encoded surface.

Playtest cannot prove an entire product correct. It can become a trustworthy release signal for the routes, states, transitions, and business rules a team explicitly registers. Anything outside that contract remains unknown.

Release eligible=contracts green+required transitions covered+no unresolved high-risk finding+no emergent regression

Actor and grader design

Better prompts help—but only after coverage is forced.

A
Actor protocol

Act, then verify the delta

The actor should still behave like a person during discovery. In release mode it also receives explicit obligations that it must execute and verify.

  1. Record before state. Name the value, route, control, or message expected to change.
  2. Perform the required action. Do not substitute a workaround before recording the failed path.
  3. Record after state. Point to concrete changed or unchanged evidence.
  4. Refuse to infer success. No error is not proof; a click is not a receipt; goal completion is not transition correctness.
  5. Return unknown honestly. If the state cannot be observed or the action was skipped, say so.
Required output per obligation{ executed, before, action, after, observed_delta, confidence }
G
Grader protocol

Judge evidence, not the actor’s story

The grader must independently read raw trajectory evidence. The actor’s conclusion is a claim to test, not a trusted summary.

  1. Grade every obligation separately. Never let overall journey success mask a failed transition.
  2. Compare expectation with evidence. Reconcile before/after values, destination, copy, totals, and co-located claims.
  3. Demand an oracle source. Mark exact business truth unknown when no contract exists.
  4. Detect rationalisation. Flag “worked” when no result changed, and contradictions the actor normalised.
  5. Separate UX from correctness. A frustrating pass and a pleasant failure are different outputs.
Required output per obligation{ verdict, evidence_refs, oracle_source, contradiction, rationale }
Playtest story skills

Split one broad “write a story” skill into four jobs.

01

Journey discovery

Create realistic goals and persona context. Optimise for natural friction and unknown unknowns. Useful evidence, but never a release gate alone.

02

Risk-matrix authoring

For every changed surface enumerate happy path, invalid input, retry, retention, empty state, exact boundaries, recovery controls, permissions, and interruption.

03

Deterministic regression

Compile one fault or obligation into explicit setup, required action, observable postcondition, and failure condition. Remove optional language from the critical path.

04

Contract-oracle authoring

Extract exact expected values from specifications, APIs, schemas, or business rules. Keep these assertions outside the LLM’s judgment.

Minimum story contract

A story is gateable only when each field is explicit.

The current natural-language stories remain valuable for exploration. A release story adds a compiled obligation layer the harness can validate before the actor starts.

obligation: checkout-empty-redirect
precondition: cart.items = 0
action: navigate("/checkout")
observe: [url, heading, payment_form]
expect:
  url: "/cart"
  payment_form: absent
oracle: contract.checkout.empty_redirect
if_action_skipped: NOT_COVERED
if_oracle_missing: UNKNOWN
Story lint should reject

unseeded preconditions · optional critical actions · unobservable postconditions · missing oracle source · success defined only by goal completion · reports that ask about behaviour the story never forced

PR-level behavioural review

Acceptance-driven hill climbing

Build-system integration

Yes—but as a bounded repair loop, not a self-merging oracle.

1

Trigger

PR opened, preview ready, or feature flag deployed. Select journeys from changed surfaces and risk metadata.

2

Gate

Run unit, integration, security, and contract checks first. Do not spend agent runs on a deterministically broken build.

3

Explore

Run Playtest personas and adversarial obligations. Emit finding class, evidence, severity, coverage, and oracle source.

4

Repair

Give an isolated coding agent only verified findings and repository context. Require a pinned regression for each fix.

5

Bound

Stop after a small retry budget, repeated failure, scope expansion, or any unknown high-risk obligation. Escalate to a human.

6

Decide

Publish separate checks for contracts, coverage, unresolved findings, and emergent regressions. Humans retain merge authority.

Recommended adoption sequenceBrownfield PR check→Feature-level repair loop→Greenfield acceptance loop→Release gate, only after validation

The study demonstrated a closed repair mechanism on one controlled app, not an unattended CI product. Branch protection and passing status checks are established merge controls; contemporary coding agents can work on branches and iterate on pull requests. Playtest can connect those pieces, but its own check must report coverage and truth separately before it is safe to require.

Industry context: coding agents create and update pull requests; protected branches require passing checks. Product efficacy claims on this page come from the hill-climb ledgers, not those external sources.
